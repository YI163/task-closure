# DSH Agent Team 协作与执行规则

版本：0.1

## 1. 总原则

使用 Agent Team 是为了提升独立研究、实施和验证的质量，不是为了让每一步都由不同 Agent 接手。必须有一个明确的负责人对最终集成与验收负责。

**推荐模式：一位队长负责端到端，少量队员负责边界清晰的专项工作；核心实现按模块顺序推进，独立调查和独立审查可以并行。**

不要默认每个 Agent 都能看到完整的历史对话或自动理解其他 Agent 的发现。共享文件和正式交接报告才是项目事实来源。

## 2. 推荐角色

### A. 队长 / 总集成负责人（必须）

唯一对产品目标、主计划、模块接口、决策记录、代码/文件集成、最终验收和用户交付负责的 Agent。

职责：
- 阅读所有项目说明文件；
- 先审计现有环境；
- 将目标拆成阶段、明确依赖与验收门槛；
- 分配任务并限制改动范围；
- 决定是否需要调用队员；
- 汇总结果，解决冲突，不接受互相矛盾的实现直接合并；
- 以证据判断完成情况；
- 在每个阶段检查是否仍服务于核心闭环。

队长不能只负责分派，不负责最终判断；不能仅因为队员说“完成”就通过验收。

### B. 产品与方法论研究员（可选，初期以只读为主）

研究任务规划、技能适配、经验记忆中真正必要的公开方法和现有可复用方案。输出简明建议、来源、适用边界和不确定性。不得在未获队长委托时改主实现。

### C. 数据与记忆设计员（可选）

审查任务状态、个人技能档案、AI 方法库和领域经验库的数据结构；识别重复、冲突、过期和隐私问题。先提交 schema/接口提案，队长批准后再按明确文件范围实施。

### D. 实施工程师（建议一次只指定一个主要写入者）

按已锁定的模块契约实施。每次改动范围要清楚，提供文件列表、测试命令、真实输出、已知限制。不得私自改变产品范围或修改其他 Agent 所拥有的文件。

### E. 独立 QA / 审查员（强烈建议）

尽量不参与被审查功能的原始实现。根据验收测试检查实现；优先尝试反例、异常路径、恢复、数据一致性、误用和边界案例。审查结果必须指出证据位置和复现方法，而不是只给主观评分。

## 3. 哪些工作并行，哪些工作串行

### 适合并行
- 只读环境审计与现有 Skill/工具盘点（前提是结果不会相互覆盖）；
- 不同主题的公开方法/开源实现研究；
- 独立编写测试场景；
- 完成实现后的独立代码审查或用户场景测试。

### 应先定义接口再并行
- 任务状态模型与 UI/交互；
- 技能库与任务规划器；
- 经验库与复盘逻辑；
- 数据层与多种功能模块。

只有当文件所有权、数据字段、函数接口、错误处理和测试契约明确后，才允许并行实现互不重叠的模块。

### 默认不适合并行
- 多个 Agent 同时写同一份核心说明文件；
- 多个 Agent 同时编辑相同的代码文件；
- 同时改动任务状态格式和依赖该格式的所有模块；
- 在整体架构仍不清晰时，让每个 Agent 自己做一个完整功能后再拼接。

如果 DSH 的 Agent Team 无法可靠控制文件隔离或交接，不要强行使用多 Agent；改为队长逐步调用单个实施 Agent，再让独立审查员检查。

## 4. 强制交接格式

每个队员的任务委派必须包括：
- 目标和需要回答的问题；
- 可读取范围；
- 可修改文件范围（默认只读，除非明确授权）；
- 禁止事项；
- 交付格式；
- 验收条件和截止边界（不需要虚构时间估算）。

队员结束时必须交付：
1. 结论与推荐；
2. 依据/证据和文件路径；
3. 实际修改文件（如有）；
4. 执行过的命令与测试结果（如有）；
5. 未完成、未知、风险和假设；
6. 队长接下来需要作出的决定。

禁止以“已完成、没问题、全部通过”等无证据表述代替交付内容。

## 5. 阶段门（Stage Gates）

### Gate 0：环境审计

确认现有 DSH 结构、Skill 加载机制、数据保存位置、测试方式、Agent Team 限制和工作区状态。阶段 0 只读，不改文件、不跑有副作用的程序。

### Gate 1：设计锁定

形成简洁架构说明、数据模型、模块边界、MVP 计划与验收映射。设计要足够明确以支持实施，但不需要为未来未知需求过度设计。

### Gate 2：核心闭环

先实现任务接收、计划生成、状态保存/恢复、进度更新和最终验收。用少数真实场景端到端验证。

### Gate 3：能力和经验记忆

加入个人技能档案、技能适配、领域经验检索/写入，并证明它们真正影响下一次任务，而非仅能保存文本。

### Gate 4：独立验收与交付

执行全部相关测试，记录失败及修复，提供最终用户手册、实际能力、限制和证据。

不要在 Gate 2 的闭环尚未跑通时，转而构建复杂界面、向量数据库、多 Agent 自主协商或其他非必要基础设施。

## 6. 代码与数据安全

- 开始前检查 Git 状态/备份方式；若工作区不是 Git 仓库，先记录文件清单与关键文件备份方案。
- 不覆盖用户已有数据；任何格式迁移都应备份并测试回滚/恢复。
- 不泄露密钥、令牌、cookie、个人证件或公司机密到外部服务或报告中。
- 未经明确授权，不向外部发送消息、提交表单、购买、发布、删除或修改权限。
- 不执行来源不明的脚本或下载后直接运行的工具；先检查其目的和副作用。
- 只安装实现核心功能必需的依赖；说明来源、权限和维护负担。
- 如果发现可能暴露隐私、破坏数据或造成不可逆后果的操作，暂停相关操作，给出风险和安全替代方式。

## 7. Harness Engineering / 可靠性要求

把自然语言目标落实为可验证的工程约束：
- 每个需求都对应至少一个验收测试或可检查证据；
- 重要的数据变更有 schema、校验和错误处理；
- 写操作有明确边界，关键数据更新可恢复；
- 测试说明真实运行环境、命令和结果；
- 修改前后检查差异，不把未执行的测试报告为通过；
- 失败必须被记录，不允许为了“全绿”删除或弱化测试；
- 对关键流程使用可重复的测试数据；
- 优先把验证放进工具/脚本，而不是完全依赖模型口头自检；
- 对随机、外部依赖或模型输出造成的不稳定性，设计边界与降级路径。

## 8. 面向用户的报告格式

每个阶段结束后，用普通中文简要说明：
- 本阶段目标；
- 已完成事项与用户能看到的变化；
- 实际测试及结果；
- 未完成/风险/已知限制；
- 是否继续推进核心闭环；
- 下一阶段的必要工作。

无需用户逐步转达队员的工作。队长必须自行组织团队、整理冲突、更新文档并提出可执行的下一步。只有涉及产品方向、个人偏好、外部授权或不可逆决定时才向用户提问；其他可逆细节自行作出合理选择并记录。
