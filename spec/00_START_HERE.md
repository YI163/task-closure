# Task Navigator：交给 DSH 的启动说明

版本：0.1  
日期：2026-10-14  
用途：本文件是整个项目的入口。请先阅读本文件，再阅读同目录的其他项目文件。它们共同构成需求与验收依据。

## 你的任务

请在当前 DSH 环境中，自主研究、设计、实现并验证一个通用的「任务执行导航员」（暂名 Task Navigator）。它应帮助用户把来自工作、生活、学习、家庭事务或个人项目的模糊任务，转化为有依据、可执行、能跟踪、可调整、最终可验收的任务闭环。

这不是只生成一段建议或漂亮流程图的聊天提示词。目标是让用户在任务进行中回来更新状态时，系统仍然知道当前任务、过去已完成什么、还缺什么、下一步最值得做什么，并能合理使用个人技能档案和领域经验库。

## 必读文件顺序

1. `01_PRODUCT_SPEC.md`：产品目标、用户场景、核心流程、范围与非目标。
2. `02_AGENT_TEAM_PLAYBOOK.md`：Agent Team 的分工、协作、执行和安全规则。
3. `03_SKILLS_AND_EXPERIENCE_MEMORY.md`：个人技能库、AI 方法库、任务状态与领域经验库的概念及数据规则。
4. `04_ACCEPTANCE_TESTS.md`：验收场景、通过标准和交付证据要求。

如有冲突：安全边界和用户明确要求优先；其次以 `01_PRODUCT_SPEC.md` 的目标与范围为准；数据规则以 `03_SKILLS_AND_EXPERIENCE_MEMORY.md` 为准；验收以 `04_ACCEPTANCE_TESTS.md` 为准。不要自行悄悄改变产品目标；如确需改变，先形成书面决策记录。

## 执行方式：先检查，再分阶段实施

### 阶段 0：环境与现状检查（只读）

先检查当前工作区、现有 Skill/插件结构、可用文件读写能力、持久化方式、测试能力、Agent Team 的真实能力和项目当前状态。不要假定某个工具、目录、数据库或 Agent Team 功能一定存在。

输出一份简洁的 `IMPLEMENTATION_PLAN.md`，说明：
- 已确认的环境事实及其证据；
- 现有可复用组件；
- 推荐的最小实现形态及原因；
- 文件/数据存储方案；
- 分阶段计划、风险、测试和验收办法；
- 哪些事项仍然不确定，以及如何以低成本验证。

完成环境检查后，不要只停留在写计划。若没有涉及不可逆操作、外部发送或重大产品方向变更，应依据本说明继续实施最小可用版本。遇到不确定但可逆的技术选择时，采用最简单、可维护、容易验证的方案，并记录假设。

### 阶段 1：实现可用的最小闭环（MVP）

优先实现：
1. 任务接收与目标澄清；
2. 复杂度/风险/任务类型判断；
3. 背景研究与来源/不确定性标记（仅在任务需要时）；
4. 方法论与任务所需技能识别；
5. 个人技能状态适配与替代/指导方案；
6. 分步骤计划、流程图、产出、依赖、完成标准、沟通节点和异常处理；
7. 任务进度持久化、恢复和下一步建议；
8. 动态重规划；
9. 结果验收与复盘；
10. 在复盘后，经过筛选地更新领域经验库和个人技能档案。

实现可以是 DSH 原生 Skill、工作区文件、轻量脚本或现有机制的组合。不要为了“像一个完整产品”而预先构建复杂前端、独立服务或庞大数据库。应先确认 DSH 现有机制是否足够。

### 阶段 2：测试与修复

根据 `04_ACCEPTANCE_TESTS.md` 逐项测试。测试证据必须能追溯到实际执行，不可把“模型认为通过”当成通过。修复关键失败后重跑回归测试。

### 阶段 3：交付与可理解说明

交付时必须说明：
- 新建和修改了哪些文件；
- 用户如何启动、使用、恢复和结束任务；
- 技能和经验数据存在哪里、如何查看/修改/删除；
- 测试执行了什么、实际结果是什么；
- 已实现、未实现、暂时无法实现的内容；
- 已知限制和风险；
- 下一步最有价值的改进建议。

请用非程序员也能理解的中文解释。不要只输出代码摘要或“全部完成”。

## 不要做的事情

- 不要擅自扩大为通用自动化平台、全功能个人助理或复杂多 Agent 框架。
- 不要先开发浏览器自动操控、自动发送消息、日历集成、云同步、向量数据库等非 MVP 必需能力。
- 不要把个人能力档案、AI 可调用 Skill 和任务经验混为一谈。
- 不要把未执行的计划记录为成功经验。
- 不要仅凭用户在 AI 指导下完成一次，就判定用户已独立掌握技能。
- 不要在没有证据时声称某流程是某咨询公司内部标准流程；公开方法要标明出处和适用限制。
- 不要为了创建 Agent Team 而把所有工作强行并行化。
- 不要让多个 Agent 同时修改同一个文件或模块，除非已明确分工并有协调机制。
- 不要删除、覆盖用户数据、改动凭证/权限、执行外部写入、发送消息或发布内容，除非已经有明确授权且风险已解释。
- 不要为了工程基础设施建设而偏离本项目的核心闭环。每个阶段都要说明它对用户完成真实任务的直接价值。

## 成功的判断

成功不是“Skill 文件创建成功”，也不是“流程图看起来专业”。成功是：用户输入一项真实任务后，系统能给出合适而不过度复杂的计划；根据用户技能调整指导；保存并恢复进度；在变化时修订计划；完成后检查结果并沉淀有证据、可复用的经验；而且这些行为都能通过测试或实际演示验证。
