# 技能体系、任务状态与领域经验库设计

版本：0.1

## 1. 为什么必须分开四类数据

### 任务状态（Task State）
回答：“这件事进行到哪里？接下来做什么？”

### 个人技能档案（User Skill Profile）
回答：“这个用户在这项具体技能上，已经能独立做到什么？”

### AI 方法/Skill 库（AI Capability & Method Library）
回答：“AI 可以调用什么指南、流程、模板或工具来完成这一步？”

### 领域经验库（Domain Experience Memory）
回答：“以前在什么条件下，用什么方法取得了什么结果？这次是否适用？”

这四类信息可以存放在同一个轻量本地存储中，但字段、更新规则和调用目的必须分开。

## 2. MVP 存储方案原则

先审计 DSH 现有持久化能力。若已有稳定的任务状态/记忆机制，优先复用；若没有，先采用简单、可检查、可备份的 Markdown/JSON 文件或现有本地数据库。不要一开始就上复杂向量数据库。

建议目录（仅为参考，需依据实际 DSH 结构调整，不要盲目创建重复目录）：

```text
Task-Navigator/
  README.md
  state/
    tasks.jsonl 或 tasks/       # 当前/历史任务状态
    user_skills.json            # 用户技能档案
    experience/                 # 按领域组织的经验条目
    decisions.md                # 重要产品/数据决策（可选）
  methods/
    index.md                    # AI 方法/Skill 索引
    ...                         # 经验证的流程、模板与检查表
  tests/
    cases/                      # 可重复测试场景
  reports/
    ...                         # 实际实施与验收报告
```

不要因为这个示意结构而拆分一堆空文件。选择最简单且与现有环境兼容的存储方式，并在实现报告中说明最终位置。

## 3. 任务状态字段

每个任务至少应保存：
- `task_id`：稳定唯一标识；
- `title` 与 `original_request`：任务名称和原始输入；
- `domain`：工作、生活、学习、个人项目或其他；
- `task_type`：研究、决策、执行、写作、协调、学习、事务处理等；
- `goal`：任务目标；
- `requester_or_beneficiary`：提出任务/使用结果的人（若相关）；
- `success_criteria`：成功标准；
- `deadline`、`constraints`、`assumptions`、`unknowns`；
- `plan`：阶段/步骤和每步的产出、依赖、完成标准、技能需求、风险及沟通点；
- `status`：未开始、进行中、等待外部输入、受阻、待验收、已完成、已取消等；
- `completed_steps` 与 `evidence`：完成记录和对应证据；
- `decisions`、`risks`、`blockers`、`changes`；
- `next_best_action`：当前下一步最值得做什么以及原因；
- `created_at`、`updated_at`、`closed_at`；
- `retrospective_status`：未复盘、待筛选、已复盘等。

计划的变更应保留简要历史或变更说明，避免新的计划覆盖后无法解释为什么变了。

## 4. 个人技能档案字段

每个技能条目至少包括：
- `skill_id`；
- `skill_name`：尽可能具体，避免“沟通能力很好”这类不可验证表述；
- `scope`：能做什么/不包括什么；
- `status`：未评估、可独立完成、可按清单完成、需逐步指导、暂未掌握、需复核；
- `evidence`：任务实例、实际操作或测试结果；
- `confidence`：判断信心及依据；
- `last_verified_at`；
- `known_gaps`；
- `preferred_learning_mode`（如已知且对任务有用）；
- `related_tasks`；
- `privacy_scope`：个人、工作、通用等必要的访问范围。

### 技能状态更新规则

- AI 解释过技能 ≠ 用户掌握技能。
- 用户在指导下完成一次 ≠ 用户能独立完成。
- 一次失败也不必自动判断用户完全不会，需考虑任务难度、工具和信息是否合适。
- 只有明确的实际表现/独立操作证据才能支持提升掌握状态；证据不足时保留原状态或标记“待验证”。
- 用户可以查看、更正或删除自己的技能档案。
- 技能会随时间变化，陈旧记录在高要求任务中应重新确认。

## 5. AI 方法/Skill 库条目

推荐字段：
- `method_id`、名称、适用任务类型；
- 解决的问题与预期结果；
- 前置条件和不适用情况；
- 所需输入和输出；
- 执行步骤；
- 检查点和失败处理；
- 来源/版本/验证状态；
- 所需工具及权限；
- 相关验收测试；
- 与其他方法的关系。

它可以包含通用方法，也可以包含领域专用方法。不要把一整篇未经验证的网络文章直接登记成可靠方法。

## 6. 领域经验库条目

每条经验至少包含：
- `experience_id`；
- `title` 与简明结论；
- `domain`、`task_type`、相关标签；
- `context`：当时的目标、约束与任务条件；
- `trigger_conditions`：什么情况下可能适用；
- `recommended_action`：建议采用的做法；
- `reasoning`：为什么可能有效；
- `observed_outcome`：真实观察到的结果；
- `evidence` 与 `source_task_id`；
- `status`：待验证、单次观察、重复支持、被反例挑战、已失效；
- `confidence`；
- `limitations` / `counterexamples`；
- `created_at`、`last_reviewed_at`、必要时的 `review_after`；
- `privacy_scope`；
- 可关联的个人技能或 AI 方法条目。

经验是“有条件的指导”，不是永远正确的硬规则。每次调用经验时，都应检查当前任务与原经验的条件是否相似、经验是否过时、是否有反例、是否与其他经验冲突。

## 7. 经验检索与使用规则

新任务开始时：
1. 从目标、领域、任务类型、约束和当前问题提取检索线索；
2. 检索少量最相关经验，不把整个经验库塞进上下文；
3. 评估相关性、证据可信度、适用条件和新鲜度；
4. 将经验作为建议或检查点，而不是自动覆盖当前任务事实；
5. 若经验与当前事实冲突，优先核实；不得盲目套用；
6. 在计划中简短说明采用了哪些经验、为什么适用；重要决定应可追溯。

建议排序时同时考虑：语义/任务相关性、条件匹配、证据质量、重复验证、时间新鲜度和负面反例。不要只因为文本相似就认为经验适用。

## 8. 复盘与经验提炼规则

复盘只回答实用问题：
- 原目标与完成标准是什么？结果如何？
- 哪些计划步骤实际有帮助，哪些是浪费？
- 发生了什么意外？根因是什么（事实与推测分开）？
- 哪些技能确实得到验证，哪些仍有缺口？
- 是否有值得未来复用的经验？适用条件和反例是什么？

写入前执行：
1. 判断是否具有跨任务价值；
2. 区分事实、解释和假设；
3. 查重并检查与已有经验的冲突；
4. 保存源任务和结果证据；
5. 根据证据设置状态，不将单次观察升级为普适规律；
6. 删除或最小化不必要的敏感信息；
7. 只有确实值得长期复用才写入。无新经验也是合法结果。

## 9. 隐私、隔离与用户控制

- 工作机密、个人生活信息和可泛化的通用经验应区分访问范围。
- 不能将公司机密直接提炼进通用经验并在其他任务中暴露。
- 长期存储只保留任务连续性、未来复用或用户明确要求所必需的信息。
- 必须提供清晰的查看、修正、导出和删除办法（按 DSH 能力选择实现形式）。
- 外部分享、云同步和向外发送记忆不属于默认行为。

## 10. 关键验收场景

- 同一个任务，用户技能状态不同，AI 提供的指导深度不同；
- 用户仅在指导下完成一次，系统不自动认定其已独立掌握；
- 任务结束后可以选择不新增经验；
- 新任务检索到相关经验，但在条件不匹配时不盲目套用；
- 经验保留真实结果、来源任务和状态；
- 任务中断后可从存储状态恢复；
- 经验或技能数据损坏/缺失时，系统诚实降级，不编造记录。
