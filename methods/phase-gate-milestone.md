# 阶段门与里程碑审查（Phase-Gate / Milestone Review）

- `method_id`: `phase-gate-milestone`
- 索引：`methods/index.json`（本文件是正文，JSON 是机器可读索引）
- `verification_status`: `unverified` ——框架的公开来源已在线核验；本条目步骤尚未在真实任务中执行验证，未验证范围见 §8
- 最近更新：2026-10-14（来源核验原始输出：`reports/METHOD_RESEARCH.md`）

## 1. 解决什么问题

跨多天/多方的任务容易一路做到底才发现方向错了；缺少「该不该继续投入」的强制停下判断点。

**预期结果**：任务被划分为若干阶段，阶段之间设可判断的进入/退出准则（门）；每个门只产生「通过 / 带条件通过 / 暂停 / 终止」四种结果，并留下依据记录。

## 2. 什么时候用 / 什么时候不要用

### 前置条件（应全部满足才使用）

- 任务跨越多天/多周，或必须等外部输入才能继续
- 阶段之间存在真实依赖（前一阶段产出是后一阶段输入）
- 有人能对门的通过与否作判断（用户本人或任务发起人）
- 允许门上做出改变方向或停止的决定

### 不适用（出现任意一条就换方法或降级为轻量清单）

- 单步、短时即可完成的任务——设门变成纯仪式
- 阶段之间没有真实依赖、可以并行推进——用并行清单而非串行门
- 决策权不在场（无人能批准继续）——门会空转，应先确认谁有权决定
- 期限极紧且不存在值得中途放弃的情形——用轻量检查点替代否决门
- 用户只需要一份清单而不需要汇报节点——不要为了规范而加门

## 3. 输入与输出

**输入**

- 阶段划分草案与每阶段目标
- 每阶段的交付物与完成标准
- 门的判断人（谁批准）与判断所需材料
- 已知风险、依赖与外部时间约束

**输出**

- 阶段-门表：阶段、交付物、进入条件、退出条件、判断人、时限
- 每个门的判断记录（结论 + 依据 + 后续动作）
- 未通过时的返工或调整方案
- 写入 changes 的计划变更记录

## 4. 执行步骤

1. 按「产出性质发生变化」划分阶段（如：范围确认→资料收集→分析→交付物成型→交付与确认），不按日历切
2. 为每个门写 2–5 条可判断真假的退出准则，避免「基本完成」「差不多」
3. 明确每个门由谁判断、需要看到什么材料
4. 在计划中写明四种可能结果（通过/带条件通过/暂停/终止）及各自后续动作
5. 到点必须做门的判断并记录依据；即使结论是延续也要写下理由
6. 门上发现目标或关键假设变化时，触发重规划并写入 changes

## 5. 检查表（做完逐条核对；不能打勾就写「未核验」）

- [ ] 每个阶段都有明确输入与输出，下一阶段输入确实来自上一阶段输出
- [ ] 退出准则是可判断真假的陈述，没有「尽量」「差不多」
- [ ] 每个门都有指定判断人与判断时限
- [ ] 门的记录含结论、依据与后续动作（四选一）
- [ ] 存在「终止或改变方向」的合法路径，而不是只能前进

## 7. 失败处理

| 失败情形 | 处理动作 |
|---|---|
| 门久拖不决（无人判断） | 标为 blocked 并升级给有决定权的人，不默认自动通过 |
| 为赶进度跳过门 | 记录为风险并说明代价；把未做的判断补记到最近的下一个门 |
| 通过后才发现准则太松 | 修订该门退出准则，并把教训写为经验候选（未验证只能标 to_verify） |
| 阶段划分与实际工作不匹配（走了几步又回头） | 允许迭代，但保留阶段与门的对应说明，避免记录失真 |
