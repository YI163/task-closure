# 风险矩阵（Risk Matrix：可能性 × 影响）

- `method_id`: `risk-matrix`
- 索引：`methods/index.json`（本文件是正文，JSON 是机器可读索引）
- `verification_status`: `unverified` ——框架的公开来源已在线核验；本条目步骤尚未在真实任务中执行验证，未验证范围见 §8
- 最近更新：2026-10-14（来源核验原始输出：`reports/METHOD_RESEARCH.md`）

## 1. 解决什么问题

多条风险混在一起，无法决定先防哪一条、哪些可以接受、哪些必须升级或修改计划。

**预期结果**：一份带等级、责任人、应对方式与复查时间的风险清单，并明确哪些是必须升级的高风险、哪些残余风险被谁接受。

## 2. 什么时候用 / 什么时候不要用

### 前置条件（应全部满足才使用）

- 已列出（或能列出）具体风险事件（「某事发生」而非「有风险」）
- 能对发生的可能性与后果影响做粗分级（高/中/低即可）
- 存在可选择的应对动作（规避、减轻、转移、接受）
- 有人有权接受残余风险

### 不适用（出现任意一条就换方法或降级为轻量清单）

- 风险只有 1–2 条且显然——直接写明并处理即可
- 没有任何信息可用于判断可能性与影响——应先生成信息，否则矩阵是拍脑袋填充
- 风险已被法规/合同强制处理、没有选择余地——按既有规则执行即可
- 用矩阵制造虚假精确（无数据却把等级写成 3.7 分）——应退回高/中/低三档
- 风险清单会包含不愿被记录的敏感信息（如工作机密）——先确认存储范围与隐私边界

## 3. 输入与输出

**输入**

- 任务目标、期限与约束
- 风险事件清单（可来自 pre-mortem 或资料研究）
- 历史相似任务教训（若经验库中有，需注明其状态）
- 可用应对资源与权限
- 组织升级规则（若有）

**输出**

- 风险登记表：风险ID、描述、触发信号、可能性、影响、等级、应对方式、责任人、复查时间
- 必须升级清单（超出用户权限或影响目标的高等级风险）
- 被接受的残余风险及其批准人
- 风险与计划步骤的对应关系

## 4. 执行步骤

1. 把风险写成具体事件句（触发条件 + 后果），去掉「沟通风险」这类无法处理的表述
2. 用统一量表（高/中/低）逐条评估可能性与影响，并写下判定依据
3. 按「可能性 × 影响」定等级并确定处理优先级
4. 为每条高等级风险指定应对方式（规避/减轻/转移/接受）与责任人、时间点
5. 定义提前升级的信号（出现什么迹象就升级给谁）
6. 把缓解动作写入计划步骤，而不是只留在风险表里
7. 设置复查时间，在阶段门或进度更新时刷新

## 5. 检查表（做完逐条核对；不能打勾就写「未核验」）

- [ ] 每条风险都有触发信号与后果描述，不是笼统名词
- [ ] 可能性与影响的判定依据被写下（哪怕依据是「同类任务经验」）
- [ ] 高等级风险都有负责人与应对动作，且应对动作出现在计划步骤中
- [ ] 被标为「接受」的风险有明确批准人，不是默认忽略
- [ ] 存在复查时间；已过复查时间的等级被标注为需复核（对应 T10 的过时处理思路）

## 7. 失败处理

| 失败情形 | 处理动作 |
|---|---|
| 矩阵结论与直觉冲突 | 核对判定依据与量表口径；保留分歧并标为待确认，不硬套等级 |
| 风险清单越列越长 | 合并同类，只保留会影响决策的条目，其余转入观察清单 |
| 风险真的发生了 | 记录实际影响并与预估对比，更新计划，把教训写为经验候选（未验证标 to_verify） |
| 应对动作无人执行 | 视为阻塞并升级，不假定会自动发生 |
| 风险涉及需要授权的外部动作 | 按 T11 处理：准备草稿与清单，未获授权不执行 |
