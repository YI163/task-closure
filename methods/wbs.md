# 工作分解结构（WBS, Work Breakdown Structure）

- `method_id`: `wbs`
- 索引：`methods/index.json`（本文件是正文，JSON 是机器可读索引）
- `verification_status`: `unverified` ——框架的公开来源已在线核验；本条目步骤尚未在真实任务中执行验证，未验证范围见 §8
- 最近更新：2026-10-14（来源核验原始输出：`reports/METHOD_RESEARCH.md`）

## 1. 解决什么问题

交付物大而模糊（如「做一份季度汇报」「办一次家庭聚会」），不清楚要分成哪些工作包、依赖是什么、做到什么算完成。

**预期结果**：一份以交付物（而非动作）为节点、逐层拆到可估算可验收的工作包清单；每个工作包有编号、负责人、完成标准，可直接对接计划、责任与验收。

## 2. 什么时候用 / 什么时候不要用

### 前置条件（应全部满足才使用）

- 最终交付物或结果能被描述出来（至少有一个可指认的产物）
- 范围边界可界定：知道哪些不做
- 能给工作包做粗略估算（允许标注为估算假设）

### 不适用（出现任意一条就换方法或降级为轻量清单）

- 任务只有 1–2 个动作、不需要协调（如「把文件发过去」）——直接做
- 交付物尚未定型、还在确认用户到底要什么——先做问题树/研究，之后再来分解
- 高度不确定、边做边学的任务——用 PDCA 小步试验比一次性分解更合适
- 分解结果没有任何人会用来排期、分工或验收——纯形式化的分解是成本
- 截止时间在前而分解需要数小时——用行动清单替代，事后再补结构

## 3. 输入与输出

**输入**

- 目标与交付物定义
- 范围与非范围（含明确不做的事）
- 已知里程碑与期限
- 可用人时与技能
- 相似任务的既有结构（若经验库中有）

**输出**

- WBS 层级清单（含 1.2.3 式编号）
- 每个工作包的交付物与完成标准
- WBS 词典：负责人、输入、产出、验收方式、估算
- 工作包与里程碑/阶段的映射
- 范围外清单

## 4. 执行步骤

1. 先写最终交付物，再自上而下逐层分解（不要从动作列表倒推结构）
2. 每一层用 100% 规则检查：子项之和完整覆盖父项且互不重叠
3. 拆到「可估算、可分配、可验收」即停（通常为单人可在数天内完成的工作包），避免过度拆分
4. 为每个工作包指定一个负责人与一条可判断真假的完成标准
5. 标注每个工作包的输入依赖与前置工作包
6. 标出关键路径上的工作包及其对应里程碑
7. 复核范围外清单，确认仍被排除

## 5. 检查表（做完逐条核对；不能打勾就写「未核验」）

- [ ] 节点命名是名词性交付物而不是动词短语（出现动词即需改写）
- [ ] 同级子项互斥且合起来覆盖父项（100% 规则）
- [ ] 每个工作包有唯一编号、一个负责人、一条可判断真假的完成标准
- [ ] 最深层工作包的估算合计与期限/资源对得上，或明确写出缺口
- [ ] 范围外清单非空（确实想过不做什么）

## 6. 模板（可直接复制到任务记录或对话中填写）

```text
1  <最终交付物>
   1.1 <工作包>   负责人：____  完成标准：____  估算：____  依赖：____  里程碑：____
   1.2 <工作包>   负责人：____  完成标准：____  估算：____  依赖：____  里程碑：____
2  <第二项交付物>
   2.1 ...

范围外（明确不做）：________________________
估算假设：________________________（未确认部分标注「估算假设」）
```

## 7. 失败处理

| 失败情形 | 处理动作 |
|---|---|
| 拆到无法估算 | 停在上一层，把该部分单列为「研究型工作包」并给时间盒 |
| 两个工作包总是同时做 | 合并；一个工作包长期完不成 → 检查是否其实含多个交付物，必要时加一层 |
| 范围扩张（新增需求） | 追加 changes 记录并重估，不静默吸收进原计划 |
| WBS 与里程碑对不上 | 先核对交付物定义，而不是改日期迁就结构 |
