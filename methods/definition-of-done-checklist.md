# 完成定义与验收检查表（Definition of Done / Checklist）

- `method_id`: `definition-of-done-checklist`
- 索引：`methods/index.json`（本文件是正文，JSON 是机器可读索引）
- `verification_status`: `unverified` ——框架的公开来源已在线核验；本条目步骤尚未在真实任务中执行验证，未验证范围见 §8
- 最近更新：2026-10-14（来源核验原始输出：`reports/METHOD_RESEARCH.md`）

## 1. 解决什么问题

「做完了」没有共同标准：步骤全部勾选但交付物不达标，或关键决策人尚未确认就被当成任务完成。

**预期结果**：事先写好的完成定义与可勾选检查表；结束时能明确区分「交付物达标」「目标已实现」「仍依赖他人确认」三种状态，并有证据位置。

## 2. 什么时候用 / 什么时候不要用

### 前置条件（应全部满足才使用）

- 存在可描述的交付物（文档、数据、活动结果、决定）
- 能事先写出至少一部分可判断的验收标准
- 有人在结束时做验收判断（用户/发起人，或 AI 与用户共同）

### 不适用（出现任意一条就换方法或降级为轻量清单）

- 结果完全由外部决定、无法预先定义标准（如等待抽签结果）——只能写清我方完成范围，不能写成果标准
- 目标本身尚未确定（还在探索要什么）——先确认目标，否则标准会写空
- 检查表被当成形式（全部打勾却无人看内容）——会制造虚假安全感，应先修复验收角色
- 救急任务且时间极紧——可以事后补检查，但必须标注标准是事后补写的
- 一次性小事（如「明早带伞」）——一句完成标准已足够，不需要表

## 3. 输入与输出

**输入**

- 目标与成功标准
- 交付物清单及其预期用途/使用者
- 外部要求（格式、规格、期限、合规）
- 谁做最终确认
- 已知风险与不可控因素

**输出**

- 完成定义（DoD）：交付物满足哪些质量条件才算完成
- 验收检查表：逐条可判断真假，并注明证据形式/位置
- 三态结论：我方完成 / 待他人确认 / 未实现
- 遗留问题与后续责任清单

## 4. 执行步骤

1. 从「谁要用它、用来做什么决定」出发写完成定义，而不是罗列工作步骤
2. 把每条标准改写成可判断真假的句子（能回答是/否），并注明证据形式
3. 检查表覆盖三类：交付物质量、过程要求（如来源标注）、目标实现条件
4. 在任务开始或中途就把检查表给用户并允许修改
5. 结束时逐条核对并写明证据位置；无法核验的条目必须标为「未核验」
6. 单独回答：原始目标是否实现？还有哪些依赖他人？
7. 未通过条目要么修复、要么明确列为遗留事项，不得静默关闭

## 5. 检查表（做完逐条核对；不能打勾就写「未核验」）

- [ ] 每条标准都能被第三方复核（含证据位置或可复现操作）
- [ ] 检查表区分「交付物完成」与「目标实现」，不把步骤勾选当作目标达成
- [ ] 依赖外部确认的事项写成「待确认」，不写「已完成」
- [ ] 不存在打勾但无证据的条目
- [ ] 未测试/未核验的内容被明确标注，不用「应该没问题」表述

## 6. 模板（可直接复制到任务记录或对话中填写）

```text
交付物：____________  使用者：____________  用途/支持什么决定：____________

完成定义（交付物满足哪些质量条件才算完成）：
- [ ] 条件 1（证据位置：____________）
- [ ] 条件 2（证据位置：____________）

过程要求（如来源标注、格式、合规）：
- [ ] ____________

目标实现条件（不是步骤勾选）：
- [ ] ____________

结论三态：□ 我方完成（交付物达标）  □ 待他人确认（写明谁、确认什么）  □ 未实现（写明缺口）
未核验条目（不得当作通过）：____________
```

## 7. 失败处理

| 失败情形 | 处理动作 |
|---|---|
| 结束时发现标准太松或太严 | 记录问题并修订 DoD 供下一次使用，不为通过而临时降低标准 |
| 关键条目无法核验 | 标记未核验并说明原因与影响，不得当作通过（对应 T13） |
| 交付物达标但目标未实现 | 明确「我方工作完成，最终目标待确认」，并列出依赖他人的事项 |
| 用户与 AI 对「完成」判断不一致 | 以事先写好的标准为准；标准缺失时补写并说明是事后补的标准 |
| 外部依赖方迟迟不确认 | 标为 waiting_external 而非 completed，并把下次跟进时间写入计划 |

- Scrum Guide 的 Definition of Done 面向软件产品增量，本条目把它扩展为通用交付物检查表，属研究者改写，未逐条与原文对应
- spec/04 §4 的 DoD 是针对本项目 MVP 的验收清单，不是通用任务方法
- 检查表能否真正阻止「勾选即完成」的误判，需在真实任务中验证
