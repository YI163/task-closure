# 规划深度判定规则（reference）

用于回答一个具体问题：**这件事该花多少规划成本？**
依据：`spec/01_PRODUCT_SPEC.md` §4B——「不允许所有任务都使用同一套冗长 SOP。规划本身也有成本，应与任务价值相称。」

## 判定顺序（先命中先定档）

1. **有不可逆后果 / 涉及资格或安全 / 花大钱？** → `deep`
   例：买房、签合同、证件办理、涉及人身安全的操作、公司对外发布。
2. **依赖多方决策？**（结果需要别人点头）→ 至少 `standard`，通常 `deep`
   例：给经理汇报、跨部门协调、家庭共同决定。
3. **需要外部信息才能决定怎么做？**（研究型）→ 至少 `standard`；若来源多、结论有争议 → `deep`
   例：买净水器、选方案、比价。
4. **步骤数 ≥ 3 或含一个需要判断的决策点？** → `standard`
5. **其余**（低风险、目标清楚、1–2 步、做错也能轻松撤回）→ `light`

## 三档的具体差异（脚本层可验证）

| 维度 | light | standard | deep |
|---|---|---|---|
| 步骤数 | 可只有行动清单 | 3–8 步 | 不限，含分支与阶段门 |
| 每步 `completion_criteria` | 可省略 | **必须** | **必须** |
| 每步 `deliverable` | 可省略 | **必须** | **必须** |
| 时间估算 | 不需要 | 需要，且写 `estimate_basis` | 需要，分段估算 + 假设 |
| 背景研究 | 不做 | 仅关键事实 | 系统研究 + 来源分级 |
| 方法与理由 | 不写 | 一句话说明 | 明确方法 + 为什么不选其他 |
| 风险 | 不写 | 主要风险 + 备用路径 | 风险矩阵 / pre-mortem |
| 沟通节点 | 无 | 仅必要节点 | 阶段门 + 升级规则 |
| 验收方式 | 用户自己看结果 | 对照成功标准 | 含外部确认项与不可控说明 |
| 是否建档 | 建（轻量） | 建 | 建 |

## 允许「降档」与「升档」的时机

- **升档**：执行中发现依赖多方、或出现不可逆后果、或反复返工 → 用 `task_update.py change` 升级深度并说明原因。
- **降档**：用户明确说「这个不重要，先随便弄」→ 降档，但要在 `changes` 里记录，并说明因此放弃了哪些质量标准。

## 反模式（判定失败）

- 用户问「提醒我带伞」，却生成含 WBS、RACI、阶段门的项目计划。
- 用户要把结论给老板决策，却只给一段没有来源、没有成功标准的建议。
- 为了显得专业，把 5 个框架叠在一个 3 步任务上。
- 三档只是标签不同，实际产出完全一样（可通过对比 `CORE_LOOP_EVIDENCE.md` 里的三个样例检查）。
