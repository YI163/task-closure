# 技能适配与「不得虚假升级」门禁（reference）

依据：`spec/01_PRODUCT_SPEC.md` §4D、`spec/03_SKILLS_AND_EXPERIENCE_MEMORY.md` §4、验收 T04/T05。

## 1. 技能状态的含义（严格定义）

| 状态 | 含义 | 允许的证据类型 |
|---|---|---|
| `not_assessed` | 从未评估 | 无 |
| `can_independently` | **在无指导下**成功完成过 | `independent_operation` 或 `observed_test` |
| `can_with_checklist` | 照清单能做，但还不能脱稿 | `independent_operation` / `observed_test`（可带清单） |
| `needs_step_by_step` | 需要逐步指导才能完成 | 任意证据 |
| `not_yet` | 目前做不到 | `failed_attempt` 或用户自述 |
| `needs_review` | 记录陈旧，高要求任务前需重新确认 | 原证据 + 超过复核期 |

## 2. 强制门禁（由 `scripts/validate.py` 检查，模型无法绕过）

- 状态为 `can_independently`，但证据里**没有** `independent_operation` 或 `observed_test` → **校验失败**。
- 这条门禁的用途：**「我在 AI 指导下完成了一次」永远不能写成「可独立完成」。**

## 3. 三种情况必须区分（写进证据的 `description`）

| 情况 | 记录方式 | 状态变化 |
|---|---|---|
| AI 讲解过某个技能 | **不写进技能档案**（那是 AI 方法库的事） | 无 |
| 用户在指导下完成一次 | 证据 `kind=guided_practice`，注明「在指导下完成」 | **保持原状态**，可加注 `known_gaps` |
| 用户独立完成 | 证据 `kind=independent_operation`，写明做了什么、结果如何 | 可升级为 `can_independently` |

## 4. 独立掌握的验证方式（T05 要求「说明需要何种表现」）

在用户只用过指导式完成时，主动给出低风险验证建议，例如：
- 「换一个同类但不同的数据/场景，你自己做一遍，做完告诉我结果。」
- 「不看我的步骤，写出你会怎么做的前三步。」
- 「这次我只在你卡住时回答，不主动给步骤。」

**通过验证前，不升级状态。**

## 5. 一次失败不等于不会

`failed_attempt` 要同时记录：任务难度、工具是否合适、信息是否充足。
只有排除这些因素后，才能判断为 `not_yet`。

## 6. 技能缺口 → 指导方式（与 SKILL.md §1D 对应）

选择路径时同时考虑三件事：**期限是否紧、失败代价是否高、学习价值是否大**。

- 期限紧 + 代价高 + 无学习价值 → **替代方案或请人协助**，不要临场教学。
- 期限宽松 + 有学习价值 → **边做边教**，但明确标注「这是在教你，不是你已掌握」。
- 用户明确说「我不想学，只想搞定」 → 尊重选择，走替代路径。

## 6.1 「谁来做」先于「怎么教」——此判断必须留下依据

上面六档只回答「怎么教」，但更前面的问题是：**这件事该用户做，还是 AI 替你做？**

**默认规则**：凡是**用户自己的生活／工作／学习事务**（装修、备考、求职、家庭安排、给谁写点什么），**默认由用户执行、AI 指导**。AI 代做需要理由，且理由必须写进任务里。

四条可接受的代做理由（满足其一即可，但必须写明是哪一个）：

1. 期限极紧，来不及学；
2. 失败代价高（涉及资格、安全、大额钱财）；
3. 纯机械劳动，没有学习价值（例如把 200 行数据排版）；
4. 用户明确说「你帮我弄好，我不想学」。

**必须写进计划的字段**：每一步的**执行者**（用户／AI／共同）。缺执行者或理由，视为计划不完整。

### 这个规则是怎么来的（真实事故）

首次真实任务（2026-10-15）中，AI 把计划写成了「我做，用户只需提供输入」，用户当场纠正——
**他要的是指导他做，不是替他做。**

（原文引用与任务细节已移除：本文件会随分享包对外分发，不应包含具体用户的私密对话。）

此时本文件 §6 与 SKILL.md §1D 已经写明了「期限宽松 + 有学习价值 → 边做边教」，但 AI 在写计划时**完全没有查阅它**，凭默认假设行事。所以规则不是不够，而是**没有被查阅**。

**因此本条同时规定动作**：写计划前必须先重读 SKILL.md §0.4 的自检表并逐项对照——**凭记忆不算，只有被查阅的规则才有效**。


## 7. 数据缺失时的诚实降级

技能档案不存在或没有该技能条目时：
- **不要**假定用户会，也**不要**假定用户不会；
- 在计划里标为 `not_assessed`，给一个低风险的探路步骤，或在开始前用一句话确认；
- 绝不因为「这类人一般都会」就跳过适配。

## 8. 自由文本技能引用 → 何时提升为档案条目

`required_skills[].skill_ref` 允许两种写法：指向档案里某个 `skill_id`，或是一段自由文本（如「需求澄清」）。自由文本是合法的，它解决「任务需要一项技能、但档案里还没这条记录」的问题。

**但它有代价**：自由文本不与档案交叉引用，因此档案变化时不会暴露失效，也无法承载「这个人到底能不能独立做到」。

**提升规则（由队长在复盘阶段检查，不自动执行）**：

- 同一个自由文本 `skill_ref` 在 **≥3 个不同任务**中出现 → 视为一项真实、反复出现的能力需求，应据此在 `state/user_skills.json` 建立正式条目（状态填 `not_assessed`，除非有独立操作证据），并把相关任务的引用改指该 `skill_id`。
- 只出现在 1–2 个任务里 → **保持自由文本**，不要为一次性需求造档案条目。档案越干净越有用。
- 提升时必须**从证据出发**：有独立操作证据才能给「可独立完成」，只有自述就填 `not_assessed` 或 `can_with_checklist`（见 §1–§3 的门禁）。
- 用户明确要求建档的技能，不受出现次数限制。

**反模式**：把每一个自由文本都提升成档案条目（档案变成垃圾场）；或者永远不提升（档案永远不知道用户缺什么）。
